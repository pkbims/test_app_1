It's still your room.

A visual pass over the eight screens that exist today — same flow, same data, same decisions already locked in the PRD (stacked before/after, image-card styles, tap-to-remove). Nothing here changes what the app does; it changes what it feels like to use. Click through the screens below in order, or jump with the rail on the left. Where there's a genuine layout choice — the Home screen, mainly — both directions are built so you can compare them side by side, not just take my word for one.

Grounded in: DecorAI's App Store listing and marketing site, and a Houzz redesign case study, both converge on the same pattern for this category — photography-forward layouts, muted/neutral chrome, minimal borders, whitespace doing the separating instead of lines. That's the starting hypothesis here, tuned warmer than DecorAI's blue-tinted neutral because this product's photography (real rooms, real light) is warmer than a generic tech-app palette suggests. The six style-sample photos already in the app are the proof — they look like a design magazine, and the chrome around them should get out of the way rather than compete.

·The system

One palette, one type pairing, one photography rule, reused on every screen so restyling later stays cheap — change a token here, not five screens.

A mosaic of three style photos instead of one — it implies range ("look what's possible") rather than showing a single static room. Headline and CTA both sit inside the photo now, using Apple's .white button style for contrast on dark.

2Home

The screen you called out. Today it's a plain text list — label and date, no image — with "New Room" as a bordered button. The room's own photography is the strongest thing this product has; it currently isn't on the one screen someone opens every time. Two real directions below, built full-size so you can compare them as you'd actually see them, not toggle between descriptions.

Depends on a small contract change. GET /v1/rooms today returns roomId, label, createdAt, hasPhoto, hasInventory — no image URL. Both directions below need a thumbnail (the room's photo, or its latest render's after_url) added to that response to work for real. That's additive to an existing endpoint, not new business logic, so it should stay cheap — flagging it because it's a real dependency, not a visual-only change.
